# WebFetch와 비교한 측정 결과

페이지 URL을 준 웹 문서 질문 30개를 한국어와 영어로 각각 풀었을 때, jevfetch의 평균 에이전트 실행 시간은 두 언어 모두 WebFetch보다 47% 짧았다. 관측된 평균 비용은 한국어에서 7%, 영어에서 3% 낮았고, 두 언어 모두 95% 구간이 차이 없음을 포함한다. 루브릭의 필수 사실 확인 116건을 WebFetch는 두 언어 모두 충족했고, jevfetch는 한국어 115건, 영어 116건을 충족했다(루브릭 항목 58개를 2회 반복, jevfetch 488ed63, Claude Code 2.1.309의 Sonnet 5.5와 WebFetch 읽기 모델 Haiku 5.5, Jev jev-1.14.0, 두 구성을 무작위 순서로 교차해 한 번에 하나씩 실행, 2026-10-23).

웹 검색은 쓰지 않았다. 보고서: [한국어](reports/agents-2026-10-23-2arm-ko/report.md), [영어](reports/agents-2026-10-23-2arm-en/report.md). 질문 30개는 페이지 21개에 있다.

질문별로 짝지은 비율(질문을 다시 뽑는 95% 부트스트랩 구간)은 WebFetch 대비 jevfetch가 비용 한국어 0.93(0.81\~1.06), 영어 0.97(0.83\~1.13), 평균 시간 0.53(0.48\~0.59), 0.53(0.47\~0.63)이다. jevfetch가 놓친 1건은 Cloud Storage 수명 주기 질문의 한국어 2회 중 1회에서 사실 3개 중 1개다. 비용과 시간은 실행이 최종 답을 낼 때까지 전부이고, WebFetch 에이전트가 `curl`로 페이지를 다시 받으러 간 턴도 들어 있다. 비용에는 jevfetch의 Jev와 WebFetch의 모든 Haiku 호출이 들어 있다. `curl` 호출은 거부된 것을 포함해 에이전트가 시도한 명령 수다.

페이지 크기(추출 토큰)별 비용과 시간 중앙값은 WebFetch / jevfetch 순이다.

크기별 사실 확인(WebFetch / jevfetch)은 중형 한국어가 74/74 / 73/74이고, 나머지 칸은 모두 충족했다(소형 24/24, 영어 중형 74/74, 대형 18/18).

WebFetch 대비 짝지은 비용비는 소형 한국어 0.90(0.82\~0.99), 영어 0.74(0.50\~1.04), 중형 0.79(0.70\~0.91)와 0.90(0.79\~1.03), 대형 1.19(0.92\~1.54)와 1.21(0.89\~1.60)이다. 평균 시간비는 모든 칸에서 0.48\~0.62다. 대형 페이지(페이지 3개에 질문 9개)에서는 jevfetch의 평균 비용이 WebFetch보다 높았고 구간은 1을 포함한다. Jev 비용은 페이지 길이에 비례하고(101,000토큰의 RFC 9110은 호출당 약 $0.022) WebFetch는 에이전트가 offset으로 다시 호출해도(실행당 1.3\~1.4회 호출, 3.2\~3.3턴) 모델 비용이 싸기 때문이다. 시간은 그래도 jevfetch가 짧고, 거기서는 둘 다 사실을 전부 찾았다.

이전 측정은 다음과 같다.

- 읽기 모델을 Haiku 4.5로 지정한 WebFetch(`ANTHROPIC_SMALL_FAST_MODEL`, 2026-10-09, Claude Code 2.1.295, 같은 질문 30개. 보고서: [한국어](reports/agents-2026-10-09-3arm-ko/report.md), [영어](reports/agents-2026-10-09-3arm-en/report.md). 지금은 평가셋에 없는 질문 2개도 함께 실려 있다). 이 구성 대비 jevfetch의 비용비는 한국어 0.56(0.48\~0.66), 영어 0.57(0.49\~0.68), 평균 시간비는 0.66(0.59\~0.73), 0.68(0.61\~0.76)이었다. Haiku 4.5 요약은 사실 확인 116건 중 한국어 114건, 영어 116건을 충족했다.
- 도구 단독 비교(영어 질문 27개, 3회, 2026-10-09, Claude Code 2.1.294)에서는 jevfetch가 81개 출력 모두에서 기준 문장을 원문 그대로 돌려줬고 WebFetch 1회 호출은 81개 중 25개였다([도구 비교](reports/webfetch-2026-10-09.md)).

이 수치의 성격은 이렇다.

- 작은 코퍼스의 파일럿이다. 페이지 21개에 질문 30개. 구간은 질문만 다시 뽑으므로 실행 간 변동이나 API 상태 변동은 담지 않는다.
- 루브릭 점수는 필요한 내용이 들어 있는지를 재는 것이지 답변 전체의 정확성이 아니다. 116은 루브릭 항목 58개를 2회 반복해 확인한 수다.
- 두 에이전트는 같은 꼴의 안내문을 받았으므로 비교 대상은 안내문을 포함한 각 읽기 도구의 구성이다.
- 시간은 도구 호출만이 아니라 Claude Code가 보고한 에이전트 과제 전체의 소요 시간이며, 프로세스 시작과 종료는 빠져 있다. 서브프로세스 벽시계 기준 WebFetch 대비 jevfetch의 평균 시간비는 두 언어 모두 0.56이다.
- Bash 허용 규칙은 `curl`, `grep`, `head`였다. 한국어 WebFetch 실행 60회 중 1회에서 명령이 거부됐고, 언어마다 WebFetch 실행 60회 중 3회에서 이 기계의 `grep`(ugrep)이 패턴을 거절했다. jevfetch 실행에는 둘 다 없었다. 그 턴들은 측정에 그대로 들어 있다.
- 비용은 프롬프트 캐시가 적용된 그대로의 청구액이다. 받아온 페이지 바이트와 Jev 요청 본문은 보관하지 않아 실행의 읽기 입력을 그대로 재현할 수는 없다.

## WebCode Highlights

Exa의 WebCode 벤치마크([exa-labs/benchmarks](https://github.com/exa-labs/benchmarks), MIT)는 코딩 질문과 그 답이 있는 페이지를 짝지어 둔 것이다. 이 중 Highlights 세트를 검색을 고정한 조건으로 썼다. 읽기 도구마다 문항의 URL과 질문을 그대로 줬다. 문항 250개 중 인용 발췌문이 가져온 페이지(jevfetch의 렌더링이나 원본 HTML)에 있는 137개를 남겼고, 나머지 113개는 뺐다. 그중 24개는 사이트가 요청을 거절한 경우다.

에이전트 단위 결과다([보고서](reports/webcode-2026-10-26/report.md). Claude Code 2.1.310, 주 모델 Sonnet 5.5, WebFetch의 읽기 모델 Haiku 5.5, Jev `jev-1.14.0`. 영어 질문, URL을 주고 웹 검색은 끔, 질문마다 1회, 한 번에 하나씩 실행). WebFetch 실행은 2026-10-25, jevfetch 실행은 2026-10-26에 했다. jevfetch의 블록 선택이 바뀌었을 때 jevfetch 실행 137회만 다시 했다. WebFetch 실행은 jevfetch를 쓰지 않기 때문이다.

| 읽기 도구 | 정답으로 판정된 답 | 원래 채점 | 질문당 평균 비용 | 그중 주 모델 | 그중 읽기 모델 또는 Jev | 주 모델 입력 토큰 | 시간 중앙값 |
|---|---|---|---|---|---|---|---|
| WebFetch, Haiku 5.5 (2026-10-25) | 137개 중 132 | 126 | $0.0149 | $0.0131 | $0.0018 | 9,447 | 12.1초 |
| jevfetch (2026-10-26) | 137개 중 137 | 136 | $0.0180 | $0.0168 | $0.0011 | 12,647 | 8.1초 |

137개 질문 단위로 짝지은 결과(질문마다 1회, Claude Code 2.1.310, 질문을 다시 뽑는 95% 부트스트랩 구간), 2026-10-26의 jevfetch 실행은 2026-10-25의 WebFetch 실행 대비 평균 시간 0.69(0.66\~0.72), 비용 1.20(1.13\~1.28)이고, 원래 채점 기준으로 질문당 정답이 0.07 많다(0.03\~0.12). 두 읽기 도구는 하루 차이를 두고 실행했으므로, 시간 비율에는 두 세션 사이의 API 지연 변화도 섞여 있다. 비용 차이는 주 모델이 jevfetch의 원문 그대로인 출력을 읽는 몫이다. 이 출력은 WebFetch의 요약보다 길다. Jev 자체는 2026-10-26의 jevfetch 실행 137회 평균으로 질문당 $0.0011이었다.

보고서의 원래 채점은 Sonnet 판정기에게 답이 기대 답 전체를 말하는지 묻는다. 그런데 Highlights의 기대 답은 질문이 묻는 것보다 더 설명하는 경우가 많아서, 맞는 플래그를 답해도 이유를 빼면 오답이 됐다. `bench/webcode.py regrade`로 각 답이 질문이 묻는 것을 답했는지 다시 물었다. 답마다 3표이고, 판정기에게는 어느 읽기 도구 쪽 에이전트가 쓴 답인지 알려 주지 않았다. 다만 답 274개 중 24개는 본문에 WebFetch나 jevfetch를 직접 언급한다([요약](reports/webcode-2026-10-26/regrade.txt)). 표는 모두 만장일치였다. 답 274개(읽기 도구마다 137개, Claude Code 2.1.310) 중 오답에서 정답으로 바뀐 판정이 7개(2026-10-25의 WebFetch 답 6, 2026-10-26의 jevfetch 답 1)였고 반대 방향은 없었다. 7개는 모두 직접 읽었고 질문에 맞게 답했다. 여전히 오답인 WebFetch 5개는 WebFetch에 HTTP 403이나 503을 돌려준 페이지 4개와, 사이트 메뉴와 푸터만 받은 페이지 1개다. 이 5개도 직접 읽었다.

도구 단위 결과다([요약](reports/webcode-2026-10-26/tools.txt). Jev `jev-1.14.0`, WebFetch는 Claude Code 2.1.310으로 호출). 모든 읽기 도구가 페이지를 가져온 133개에서, 같은 방식의 판정기가 기대 답에 필요한 정보가 있다고 본 출력은 2026-10-26의 jevfetch 133개, 2026-10-25의 WebFetch 1회 호출 120개와 이어 읽기를 포함한 WebFetch 123개였다. 이 133개 중 인용 발췌문이 원문 그대로 들어 있는 출력은 jevfetch 121개, WebFetch 10개와 10개였다. 같은 133개에서 도구 시간 합계는 jevfetch 124초(2026-10-26), WebFetch 420초와 453초(2026-10-25)였다.

이 수치의 성격은 이렇다.

- 질문마다 1회, 영어, 코딩과 개발 문서 페이지다. 구간은 질문만 다시 뽑는다.
- 문항은 가져온 페이지에 발췌문이 있는지로 골랐다. 모든 요청을 거절한 페이지나 발췌문이 더는 없는 페이지는 137개에 없다.
- 페이지는 실행마다 실시간으로 가져왔고, 페이지 바이트는 보관하지 않았다. jevfetch와 WebFetch는 각 페이지를 다른 시각에 가져왔다(에이전트 단위는 하루, 도구 단위는 약 90분 차이). 그사이 바뀐 페이지는 같은 바이트로 비교되지 않았다.
- 여기서 잰 jevfetch는 [동작 방식](../README.ko.md#동작-방식)에 적은 것이고, 후보 기준은 0.6이다. 문항 하나(`highlights_215`)는 답이 `<aside>`로 쓴 참고 상자 안에만 있다.

측정 방법은 [bench/README.md](README.md)를 참고한다.
