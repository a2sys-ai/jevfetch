# WebFetch와 비교한 측정 결과

페이지 URL을 준 웹 문서 질문 30개를 한국어와 영어로 각각 풀었을 때, jevfetch의 평균 에이전트 실행 시간은 Haiku 5.5를 쓰는 WebFetch보다 43\~49%, Haiku 4.5를 쓰는 WebFetch보다 32\~34% 짧았다. 관측된 평균 비용은 Haiku 5.5 대비 한국어에서 11% 낮고 영어에서 1% 높았으며(두 언어 모두 95% 구간이 차이 없음을 포함) Haiku 4.5 대비 43\~44% 낮았다. 루브릭의 필수 사실 확인 116건은 언어마다 jevfetch와 Haiku 5.5 WebFetch가 모두 충족했고, Haiku 4.5 WebFetch는 한국어 114건, 영어 116건을 충족했다(루브릭 항목 58개를 2회 반복, Claude Code 2.1.295, Sonnet 5.5, 세 구성을 무작위 순서로 교차해 한 번에 하나씩 실행, 2026-10-09). 30개는 WebFetch가 읽기 모델을 거쳐 답한 질문이고, 뺀 2개는 아래에 적었다.

웹 검색은 쓰지 않았다. Haiku 5.5는 이 실행에서 Claude Code가 쓴 읽기 모델이고, 그 전 모델인 Haiku 4.5는 `ANTHROPIC_SMALL_FAST_MODEL`로 지정했다. 보고서([한국어](reports/agents-2026-10-09-3arm-ko/report.md), [영어](reports/agents-2026-10-09-3arm-en/report.md))는 질문 32개를 담고 있고, 아래 표와 비율에서는 그중 2개를 뺐다. 두 질문의 페이지(redis.io, docs.stripe.com)는 요청하면 마크다운을 주고, 두 질문의 WebFetch 실행은 모두 읽기 모델을 부르지 않고 페이지 전체를 그대로 에이전트에 넘겼으므로 WebFetch의 답을 재지 못한다. 거기서 WebFetch 실행은 모두 사실을 전부 맞혔고, jevfetch는 Stripe에서 전부, Redis EXPIRE에서는 매번 4개 중 3개를 맞혔다(선별이 한 문장을 뺐다). 아래 수치는 나머지 질문 30개(페이지 21개)다.

질문별로 짝지은 비율(질문을 다시 뽑는 95% 부트스트랩 구간)은, Haiku 5.5를 쓰는 WebFetch 대비 jevfetch가 비용 한국어 0.89(0.79\~1.004), 영어 1.01(0.86\~1.18), 평균 시간 0.51(0.47\~0.56), 0.57(0.51\~0.63)이다. Haiku 4.5를 쓰는 WebFetch 대비로는 비용 0.56(0.48\~0.66), 0.57(0.49\~0.68), 평균 시간 0.66(0.59\~0.73), 0.68(0.61\~0.76)이다. 두 WebFetch 행의 차이는 읽기 모델뿐이다. Haiku 4.5는 토큰당 약 7배 비싸서 "그중 메인 모델"은 비슷하고 총액만 다르며, 실행당 출력 토큰을 4\~5배 쓰는 Haiku 5.5보다 호출당 답이 빨리 나온다. Haiku 4.5 요약은 한국어에서 사실 2개를 빠뜨렸다. 비용과 시간은 실행이 최종 답을 낼 때까지 전부이고, WebFetch 에이전트가 `curl`로 페이지를 다시 받으러 간 턴도 들어 있다. 비용에는 jevfetch의 Jev와 WebFetch의 모든 Haiku 호출이 들어 있다. `curl` 호출은 거부된 것을 포함해 에이전트가 시도한 명령 수다.

크기별 사실 확인(WebFetch 4.5 / 5.5 / jevfetch)은 소형 한국어 29/30 / 30/30 / 30/30, 영어 모두 30/30, 중형 한국어 67/68 / 68/68 / 68/68, 영어 모두 68/68, 대형 모두 18/18이다.

Haiku 5.5 WebFetch 대비 짝지은 비용비는 소형 한국어 0.89(0.85\~0.95), 영어 0.98(0.77\~1.27), 중형 0.80(0.71\~0.90)과 0.88(0.80\~0.96), 대형 1.03(0.80\~1.29)과 1.23(0.86\~1.67)이다. 평균 시간비는 모든 칸에서 Haiku 5.5 대비 0.49\~0.64, Haiku 4.5 대비 0.61\~0.78이다. 대형 페이지(페이지 3개에 질문 9개)에서는 jevfetch의 평균 비용이 Haiku 5.5 WebFetch보다 높았고 구간은 1을 포함한다. Jev 비용은 페이지 길이에 비례하고(101,000토큰의 RFC 9110은 호출당 약 $0.023) WebFetch는 에이전트가 offset으로 다시 호출해도(실행당 1.2\~1.5회 호출, 3.4턴) 모델 비용이 싸기 때문이다. 시간은 그래도 jevfetch가 짧고, 거기서는 셋 모두 사실을 전부 찾았다.

에이전트가 웹 검색으로 페이지를 먼저 찾아야 하는 조건([보고서](reports/agents-2026-10-09/report.md), Redis EXPIRE와 Stripe 질문을 포함한 한국어 질문 20개, URL 없음, Haiku 5.5 WebFetch, 2개씩 동시 실행)에서는 질문당 비용이 둘 다 $0.056으로 같고(비율 1.00, 구간 0.89\~1.12), 시간 중앙값은 26.2초 대 20.1초, WebFetch 에이전트는 40회 중 9회 `curl`로 원문을 다시 받으러 갔고 jevfetch 에이전트는 1회였다. 안내 파일 대신 한 문장짜리 WebFetch 안내를 주면 WebFetch가 평균 $0.065였다([소거 실험](reports/agents-2026-10-09-ablation/report.md)). 도구 단독 비교(영어 질문 27개, 3회)에서는 jevfetch가 81개 출력 모두에서 기준 문장을 원문 그대로 돌려줬고 WebFetch 1회 호출은 81개 중 25개였다([도구 비교](reports/webfetch-2026-10-09.md)).

이 수치의 성격은 이렇다.

- 작은 코퍼스의 파일럿이다. 페이지 21개에 질문 30개. 구간은 질문만 다시 뽑으므로 실행 간 변동이나 API 상태 변동은 담지 않는다.
- 루브릭 점수는 필요한 내용이 들어 있는지를 재는 것이지 답변 전체의 정확성이 아니다. 116은 루브릭 항목 58개를 2회 반복해 확인한 수다.
- 두 에이전트는 같은 꼴의 안내문을 받았으므로 비교 대상은 안내문을 포함한 각 읽기 도구의 구성이다.
- 시간은 도구 호출만이 아니라 Claude Code가 보고한 에이전트 과제 전체의 소요 시간이며, 프로세스 시작과 종료는 빠져 있다. 서브프로세스 벽시계 기준 시간비는 Haiku 5.5 대비 0.54와 0.60, Haiku 4.5 대비 0.68과 0.71이다.
- Bash 허용 규칙은 `curl`, `grep`, `head`였다. 구성·언어마다 WebFetch 실행 2\~5회에서 명령이 거부됐고 2\~9회에서 이 기계의 `grep`(ugrep)이 패턴을 거절했다. jevfetch 실행에는 둘 다 없었다. 그 턴들은 측정에 그대로 들어 있다.
- 비용은 프롬프트 캐시가 적용된 그대로의 청구액이다. 받아온 페이지 바이트와 Jev 요청 본문은 보관하지 않아 실행의 읽기 입력을 그대로 재현할 수는 없다.
- 채점 뒤에 루브릭 표기 하나와 근접 창 하나를 고쳐 전 세트를 다시 채점했다. 창 수정으로 WebFetch 실행 하나의 사실이 하나 늘었다.

측정 방법은 [bench/README.md](README.md)를 참고한다.
