# WebFetch와 비교한 측정 결과

페이지 URL을 준 웹 문서 질문 30개를 한국어와 영어로 각각 풀었을 때, jevfetch의 평균 에이전트 실행 시간은 두 언어 모두 WebFetch보다 47% 짧았다. 관측된 평균 비용은 한국어에서 7%, 영어에서 3% 낮았고, 두 언어 모두 95% 구간이 차이 없음을 포함한다. 루브릭의 필수 사실 확인 116건을 WebFetch는 두 언어 모두 충족했고, jevfetch는 한국어 115건, 영어 116건을 충족했다(루브릭 항목 58개를 2회 반복, jevfetch 488ed63, Claude Code 2.1.309의 Sonnet 5.5와 WebFetch 읽기 모델 Haiku 5.5, Jev jev-1.14.0, 두 구성을 무작위 순서로 교차해 한 번에 하나씩 실행, 2026-10-23).

웹 검색은 쓰지 않았다. 보고서: [한국어](reports/agents-2026-10-23-2arm-ko/report.md), [영어](reports/agents-2026-10-23-2arm-en/report.md). 질문 30개는 페이지 21개에 있다.

질문별로 짝지은 비율(질문을 다시 뽑는 95% 부트스트랩 구간)은 WebFetch 대비 jevfetch가 비용 한국어 0.93(0.81\~1.06), 영어 0.97(0.83\~1.13), 평균 시간 0.53(0.48\~0.59), 0.53(0.47\~0.63)이다. jevfetch가 놓친 1건은 Cloud Storage 수명 주기 질문의 한국어 2회 중 1회에서 사실 3개 중 1개다. 비용과 시간은 실행이 최종 답을 낼 때까지 전부이고, WebFetch 에이전트가 `curl`로 페이지를 다시 받으러 간 턴도 들어 있다. 비용에는 jevfetch의 Jev와 WebFetch의 모든 Haiku 호출이 들어 있다. `curl` 호출은 거부된 것을 포함해 에이전트가 시도한 명령 수다.

크기별 사실 확인(WebFetch / jevfetch)은 중형 한국어가 74/74 / 73/74이고, 나머지 칸은 모두 충족했다(소형 24/24, 영어 중형 74/74, 대형 18/18).

WebFetch 대비 짝지은 비용비는 소형 한국어 0.90(0.82\~0.99), 영어 0.74(0.50\~1.04), 중형 0.79(0.70\~0.91)와 0.90(0.79\~1.03), 대형 1.19(0.92\~1.54)와 1.21(0.89\~1.60)이다. 평균 시간비는 모든 칸에서 0.48\~0.62다. 대형 페이지(페이지 3개에 질문 9개)에서는 jevfetch의 평균 비용이 WebFetch보다 높았고 구간은 1을 포함한다. Jev 비용은 페이지 길이에 비례하고(101,000토큰의 RFC 9110은 호출당 약 $0.022) WebFetch는 에이전트가 offset으로 다시 호출해도(실행당 1.3\~1.4회 호출, 3.2\~3.3턴) 모델 비용이 싸기 때문이다. 시간은 그래도 jevfetch가 짧고, 거기서는 둘 다 사실을 전부 찾았다.

이전 측정은 다음과 같다.

- 읽기 모델을 Haiku 4.5로 지정한 WebFetch(`ANTHROPIC_SMALL_FAST_MODEL`, 2026-10-09, Claude Code 2.1.295, 같은 질문 30개. 보고서: [한국어](reports/agents-2026-10-09-3arm-ko/report.md), [영어](reports/agents-2026-10-09-3arm-en/report.md). 지금은 평가셋에 없는 질문 2개도 함께 실려 있다). 이 구성 대비 jevfetch의 비용비는 한국어 0.56(0.48\~0.66), 영어 0.57(0.49\~0.68), 평균 시간비는 0.66(0.59\~0.73), 0.68(0.61\~0.76)이었다. Haiku 4.5 요약은 사실 확인 116건 중 한국어 114건, 영어 116건을 충족했다.
- 도구 단독 비교(영어 질문 27개, 3회, 2026-10-09, Claude Code 2.1.294)에서는 jevfetch가 81개 출력 모두에서 기준 문장을 원문 그대로 돌려줬고 WebFetch 1회 호출은 81개 중 25개였다([도구 비교](reports/webfetch-2026-10-09.md)).

이 수치의 성격은 이렇다.

- 작은 코퍼스의 파일럿이다. 페이지 21개에 질문 30개. 구간은 질문만 다시 뽑으므로 실행 간 변동이나 API 상태 변동은 담지 않는다.
- 루브릭 점수는 필요한 내용이 들어 있는지를 재는 것이지 답변 전체의 정확성이 아니다. 116은 루브릭 항목 58개를 2회 반복해 확인한 수다.
- 두 에이전트는 같은 꼴의 안내문을 받았으므로 비교 대상은 안내문을 포함한 각 읽기 도구의 구성이다.
- 시간은 도구 호출만이 아니라 Claude Code가 보고한 에이전트 과제 전체의 소요 시간이며, 프로세스 시작과 종료는 빠져 있다. 서브프로세스 벽시계 기준 WebFetch 대비 jevfetch의 평균 시간비는 두 언어 모두 0.56이다.
- Bash 허용 규칙은 `curl`, `grep`, `head`였다. 한국어 WebFetch 실행 60회 중 1회에서 명령이 거부됐고, 언어마다 WebFetch 실행 60회 중 3회에서 이 기계의 `grep`(ugrep)이 패턴을 거절했다. jevfetch 실행에는 둘 다 없었다. 그 턴들은 측정에 그대로 들어 있다.
- 비용은 프롬프트 캐시가 적용된 그대로의 청구액이다. 받아온 페이지 바이트와 Jev 요청 본문은 보관하지 않아 실행의 읽기 입력을 그대로 재현할 수는 없다.

측정 방법은 [bench/README.md](README.md)를 참고한다.
